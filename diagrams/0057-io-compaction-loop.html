io Compaction Loop — Root Cause

Why io's Telegram direct session compacts repeatedly within a single conversation, and what to fix.

OBSERVED SYMPTOM

Root Cause

A two-failure feedback loop

Two independent defects interlock. Either one alone is tolerable; together they create a self-sustaining compaction cycle.

The July 2026 refit correctly registered io's 200k window and set the threshold accordingly. The problem is not the threshold value — it's the contents that fill the window (verbose trust-check prose) and what falls out of the compaction summary (channel trust state).

Cause analysis

Three contributing factors

①
Trust check verbosity — context bloat
Every incoming message on agent:io:telegram:direct:8335771088 triggers a full multi-paragraph trust analysis. The response visible in the screenshot is ~300–500 tokens of explanation per message. When io is mid-session on a heavy task (COA retro planning with tool calls, context from prior exchanges), this routine prose accumulates fast and pushes total usage over the 160k flush line.

Why it's new: the COA retro context is denser than typical io workloads. Trust checks that were background noise previously now land near a full threshold.
②
Trust state not compaction-resistant
When compaction fires, io's session context is summarised to postCompactionMaxChars (24,000 chars). The compaction summary template does not include a trusted-channels list as a named section, so the fact that Martin confirmed 8335771088 as a verified channel is at best in the free-text summary and frequently dropped under the char limit.

After compaction, io resumes with no memory that the channel was verified. The next incoming Telegram message re-triggers the full trust check. The loop closes.
③
postCompactionMaxChars insufficient for COA sessions
24,000 chars was sized for io's typical lightweight routing workload. A COA retro planning session carries: project context, prior exchanges, action items, channel routing rules, and trust decisions. These compete for the same 24k char budget, and trust state — being meta-information about the session, not the task itself — loses to task content under compression pressure.

Even if trust state is written first into the summary, a dense COA session will push it toward the char limit and risk truncation on the next compaction.
Fixes

Proposed remediation

Priority Change Mechanism Addresses
P0 Persist channel trust to a file io writes a ~/.openclaw/trusted-channels.json when a channel is confirmed; reads it at session start before running any trust check ② — survives compaction
P0 Pin trust state as first compaction section Add trusted_channels as the first named section in io's postCompactionSections list — it is written before task content and cannot be squeezed out ② ③ — belt + suspenders
P1 Short-circuit trust check for known channels If channel id is in trusted-channels.json, emit a one-line acknowledgement instead of a full trust analysis paragraph ① — removes context bloat
P2 Raise postCompactionMaxChars for io Schema-locked at global level (finding from 0045 / issue #57174), but raising the global value from 24k → 32k helps all agents; io benefits most ③ — more room for state survival
OPT Rate-limit trust check prose Only run a full trust analysis on the first message per session from an unverified channel; subsequent messages from the same channel get a one-line note ① — reduces bloat without requiring file persistence
